## What this is

A standalone, single-file HTML tool: a Gantt chart for product roadmaps, built with Plotly.js loaded from CDN. No build step, no bundler, no npm dependencies. The entire product is one file — `index.html` — that opens directly in a browser.

## Product boundary

- **Program Increments (PI) and Sprints are overlaid as bands at the top of the chart.** Task activity bars render below them, sharing the same date-based x-axis, so PI/sprint boundaries align visually with the tasks underneath. **A PI can override the active theme's default band color** with its own manual color, same pattern as per-task color. **The whole PI/Sprint layer can be turned off** (`showPiSprint`, default `true`) for a pure task/lane/milestone Gantt chart — a display/edit-visibility toggle only, never destructive of existing PI/Sprint data.
- **Milestones are not a separate entity.** A milestone is a `TASKS` entry where `start === end` (a same-day task) — it has a lane, status, owner, and description exactly like any other task, created through the same Task form. The only difference is visual: it renders as a configurable marker (`milestoneShape`) instead of a bar. **A milestone can also be perched above or below its lane row** (`milestonePosition`) with a connector line back to its actual date, instead of always sitting directly on the row.
- **Tasks are organized into named Lanes (swimlanes), not one row per task.** All tasks assigned to the same lane (including same-day "milestone" tasks) render on that lane's single row. Lanes are independently manageable (add/edit/delete/reorder), separate from tasks themselves. **A lane can override the active theme's default row-label color** with its own manual color, same pattern as per-task/per-PI color.
- **Task color is chosen manually, per task — not derived from status.** The original status-driven legend/coloring from #6 was removed as unhelpful in practice. Each task has its own `color` field, set via a color picker in the Task form. `status` still exists as a field (visible via hover and the click-to-overlay dialog) but no longer drives any visual color or legend.
- **Tasks carry a longer freeform description, visible only via hover and click-to-overlay — never baked into the chart itself.** (1) The hover tooltip — quick-glance summary (name/date(s)/status/owner). (2) Click-to-overlay dialog with the full description. **`descriptionPosition`** (`'hidden' | 'above' | 'below' | 'inline'`, default `'hidden'`) controls the task's **name** label instead — corrected 2026-08-28 after the original design (baking description into the chart) produced duplicate/redundant text whenever a task's description matched its name, and was found to leave bars with no visible name label at all under any setting except `'inline'`. `Hidden` = no name shown; `Inline` = name inside the bar (or `name<br>date` on a milestone marker); `Above`/`Below` = name as a floating annotation instead of inside the bar/marker. Applies uniformly to regular task bars and milestone markers.
- **Bulk editing via CSV, per entity type.** Each of the four Configure sections (PIs, Sprints, Lanes, Tasks) supports exporting its data as a flat CSV and importing one back — added specifically to streamline entering many repetitive rows (e.g. a long run of Sprints) by editing them in Excel/Sheets instead of one at a time in the app. CSV was chosen deliberately over real `.xlsx`: Excel opens/saves CSV natively, so the "bulk-edit in Excel" workflow is fully achieved without needing true binary spreadsheet support or a new dependency. Import must tolerate Excel's common date-reformatting behavior on re-saved CSVs, not just strict ISO dates.
- **Chart Header and Chart Footer are editable through the Configure screen, not just hand-edited constants.** (Renamed from "Chart Title"/"X-axis Label" — same underlying settings, user-facing terminology changed.) Every other piece of roadmap content (PIs, Sprints, Lanes, Tasks) is edited via Configure; these followed the same pattern once that inconsistency was noticed. Both persist through Open/Save like the rest of the roadmap data, with safe fallback defaults (`"Product Roadmap"` / `"Date"`) for older saved files.
- **A custom `vizimap` theme is the default**, alongside the ten built-in Plotly themes, all selectable from Chart Settings. The custom theme went through two rounds (2026-08-26): the first pass was too conservative on review; round 2 covers bolder typography, a real segmented-control look for the Chart/Configure toggle (and, since then, all Configure buttons), styled row labels (matched to the same font stack and enlarged, 2026-08-27), a non-flat-white background, and a corrected chevron treatment (PI band only — it didn't translate cleanly to individual task bars, so it was removed there), all within the existing no-new-dependencies constraint (system font stack only, no CDN font).
- **A version number is always visible in the top-right corner of the page**, regardless of whether Chart or Configure is the active view — see "Versioning" below.
- **This is a personal planning tool, not a hosted service.** There is no backend, no deploy target, no container. The deliverable is the file itself.
- **This is a real roadmap-authoring tool, not just a static viewer.** The product owner creates, edits, and plans roadmaps directly in the tool — adding/editing/removing Program Increments, Sprints, Lanes, and Tasks (including milestones, as same-day tasks) through an in-app UI — to produce a clean visual to brief to leadership.
- **Two distinct view modes: Chart and Configure.** A toggle at the top of the page shows either the chart (plus PNG export) or the editing/configuration UI (PI/Sprint/Lane/Task forms and lists, Chart Settings, plus Open/Save) — never both at once.
- **Exportable to PNG** via Plotly's native mode-bar export button (configured with 2x scale and a dated filename) — the earlier custom "Export PNG" button was removed as redundant once the native button was configured to match its quality settings. The chart uses the full available viewport width (no fixed max-width) and its height scales with lane count.

## Versioning (decided 2026-08-28)

- **Format: `x.y.z` — no commit hash.** A literal commit SHA can't be baked into a file that doesn't know its own hash until after it's committed (a real chicken-and-egg problem for a plain static HTML file with no build step), and a live-fetched "as of GitHub's current state" value would be misleading for anyone viewing an older downloaded copy. Plain semantic-looking version numbers avoid both problems.
- **Displayed persistently in the top-right corner of the page**, visible in both Chart and Configure views — lives in shared page chrome outside the two toggled view containers, not duplicated inside each one.
- **Standing rule: every PR that merges to `main` increments the patch number by exactly 1** (`x.y.(z+1)`) as part of that same PR's changes — no exceptions, no judgment calls about whether a change is "big enough" to warrant a bump. This is deliberately simple: flat patch-increment only, no major/minor semantics to reason about. Update the version constant in the same commit as the rest of the change.
- **No update-checker, deliberately.** Considered and explicitly rejected (2026-08-28) as unnecessary complexity for a personal utility with no formal release process — this repo does not use GitHub Releases/tags as version checkpoints, so there's no meaningful "latest version" to check against beyond `main` itself, which changes on every merge. If someone wants the newest copy, they re-download `index.html` from the repo. Do not add a GitHub API call, a "new version available" notice, or any other network-dependent version-checking behavior without this decision being revisited explicitly first.

## Architecture

- Single file: `index.html`. HTML, CSS, and JS all inline.
- Plotly.js via CDN script tag, pinned to a specific version (`2.35.2` as of this writing) — don't float on `latest`. **No other CDN requests or dependencies are permitted** — this has been reaffirmed explicitly specifically to rule out adding a webfont service for typography improvements, and again when scoping CSV (rather than real `.xlsx`) import/export; use a strong system-font stack and a hand-written CSV parser/serializer, not new libraries. The no-update-checker decision above reflects the same "avoid unnecessary network dependency" philosophy.
- Data collections — same shapes whether they come from the built-in sample data or a loaded file:
  - `PROGRAM_INCREMENTS`: `[{ name, start, end, color? }]` — `color` is an optional hex string overriding the active theme's default PI band color for that specific PI.
  - `SPRINTS`: `[{ name, start, end, piName }]` (piName links a sprint to its parent PI for validation/grouping, not required for rendering)
  - `LANES`: `[{ name, color? }]` — display order in this array is the display order in the chart (top to bottom). No separate `order` field; reordering means reordering this array. `color` is an optional hex string overriding the active theme's default row-label color for that specific lane.
  - `TASKS`: `[{ name, start, end, status, owner?, lane, description?, color?, descriptionPosition?, milestonePosition?, milestoneShape? }]` — `lane` references a `LANES` entry's `name`, same referencing convention as `SPRINTS.piName`. `color` is an optional hex string set manually per task (not derived from status). `descriptionPosition` is `'hidden' | 'above' | 'below' | 'inline'`, default `'hidden'` — governs the task's **name** label position on the chart (see product boundary above); description itself never renders on the chart. `milestonePosition` is `'on' | 'above' | 'below'`, default `'on'`, relevant only when `start === end` — offsets the milestone marker itself off its lane row with a connector line, a separate concern from `descriptionPosition`'s name-label positioning. `milestoneShape` is `'diamond' | 'circle' | 'star' | 'triangle' | 'octagon'`, default `'diamond'`, and is relevant only to milestones. **A task where `start === end` is a milestone** — same schema, no extra entity needed, only the rendering shape differs.
  - Chart-level settings, labeled in Configure as **Chart Header** and **Chart Footer**: `CHART_TITLE` (default `"Product Roadmap"`), `X_AXIS_TITLE` (default `"Date"`), `CHART_THEME` (default `"vizimap"`), and `showPiSprint` (boolean, default `true`) — plain `let` variables, editable via Configure's "Chart Settings" section, not `const`s baked into the render function. (Internal variable/JSON-key names may or may not match the current display labels — either is fine as long as older saved files still load correctly.) A separate `APP_VERSION` constant (see "Versioning" above) holds the `x.y.z` string — this one is not user-editable and not part of the roadmap JSON schema, it's a property of the code itself.
- Gantt bars use the standard Plotly technique: `type: 'bar', orientation: 'h'`, date-typed x-axis, `base` = start date, `x` = duration. A task with `start === end` (a milestone) renders instead as a scatter-trace point using its `milestoneShape` (defaulting to `diamond`), positioned in its lane's row (or offset above/below per `milestonePosition`) like any other task in that lane.
- PI and Sprint bands render as their own rows at the top (same technique), with vertical dashed gridlines at PI/sprint boundaries extending down through the task rows below, so alignment is a literal visual gridline, not just proximity. The PI band uses a chevron/pointed-end treatment at PI boundaries; task bars do not (see above). This entire layer (bands, gridlines, Configure sections, and the Sprint/PI tick-mode options) hides when `showPiSprint` is `false`.
- **Task rows are one-per-lane, not one-per-task.** Multiple tasks (bars and/or milestone diamonds) assigned to the same lane share that lane's row. **Deliberate scope boundary:** if two tasks in the same lane have overlapping date ranges, they will visually overlap on the chart — this is accepted as useful signal (a real scheduling conflict), not a bug. Automatic sub-row packing/offsetting for overlapping same-lane tasks is explicitly out of scope unless revisited later.
- **No legend.** Removed along with status-driven coloring — it was static and unhelpful. Task color is per-task and manual (see above); don't reintroduce a legend without a specific reason to.
- **Click vs. hover — the only two ways to see a task's description, both screen-only.** Hover (native Plotly tooltip) = quick glance. Click = deliberate, on-screen dialog with the full description, dismissible. Neither survives a PNG export, and description has no third, chart-baked form (see product boundary above — that role now belongs to name via `descriptionPosition`).

## Persistence

- **Mechanism: the File System Access API** (`window.showOpenFilePicker` / `showSaveFilePicker`). "Open Roadmap" picks a JSON file from disk; edits happen in memory; "Save" writes back to that same open file handle — no server, no download-then-manually-replace-the-file step. This is the intended day-to-day workflow: the JSON file sits next to `index.html` like a companion data file, opened and saved in place.
- **Chromium-only by design, not an oversight.** The File System Access API only works in Chrome/Edge, not Firefox or Safari. Confirmed: Stan only uses Chrome/Edge, so **no fallback for other browsers is required.** Don't build one. If the API is unavailable, a clear error message is enough.
- **First-run behavior:** if no file has been opened yet, the app falls back to the built-in sample data already in the file — so `index.html` still opens and shows something meaningful with zero setup, same as today.
- **JSON schema on disk** is a single object wrapping the data collections plus chart-level settings: `{ programIncrements: [...], sprints: [...], lanes: [...], tasks: [...], chartTitle: "...", xAxisTitle: "...", chartTheme: "...", showPiSprint: true|false }` (or renamed keys reflecting Chart Header/Footer terminology — see above). Milestones need no schema entry of their own — they're just `tasks` entries. `APP_VERSION` is never part of this file — see "Versioning" above. **Any key missing from an older saved file must fall back to its built-in default, not error** — this applies to chart-level settings, per-PI/per-lane/per-task `color`, `descriptionPosition`, `milestonePosition`, `milestoneShape`, and `showPiSprint` (defaults to `true`), and to any future schema additions.
- **CSV is a separate, per-entity bulk-edit format alongside the JSON roadmap file** — not a replacement for it. CSV round-trips one entity type's data (matching its exact in-memory field list); the JSON file remains the single source of truth for a complete roadmap (all entity types plus chart-level settings together).

## Deployment

**None.** No Docker, no container, no CI-driven deploy, no Variflex-managed dev/main promotion in the usual sense — there's nothing to run as a service. CI's only job is a sanity check that the file is well-formed (parses without syntax errors); there's no build or deploy stage after that.

## Constraints

- No frameworks (React, Vue, etc.) — plain HTML/CSS/JS plus the Plotly CDN script only.
- No bundler, no npm install step, and no additional CDN requests of any kind (including webfonts, a spreadsheet library for real `.xlsx` support, or a GitHub API call for version checking — see "Versioning" above) beyond the one existing Plotly script tag. If a library is ever needed beyond Plotly, it comes from a CDN `<script>` tag as a deliberate, discussed exception — not by default.
- The JSON schema above is the API once persistence lands. Any change to its shape must be reflected here.
- Single branch (`main`). No dev/main split — there's no environment to promote between for a static file with no deploy step. PRs merge directly to `main` once CI (the sanity check) passes.
- **Every PR increments `APP_VERSION`'s patch number by 1** — see "Versioning" above. This applies to all future issues in this repo, not just ones that mention it explicitly.

## Working philosophy (inherited from Pacific Shift Labs' standing rules)

- Boring and simple first.
- Halt and log, don't self-heal — if something's ambiguous or a spec gap is found, stop and report it in the PR/issue rather than guessing silently.
- Automation presents context, it doesn't make product decisions on Stan's behalf.
- One issue worked at a time in this repo — never dispatch multiple concurrently.
- Self-merge is authorized by default once CI is green — PR code review is a post-merge job, not a pre-merge gate.
